# Лабораторная работа №4: Аутентификация, авторизация и аудит безопасности

RESTful веб-приложение для проведения торгов редкими и коллекционными предметами. Реализовано на стеке Spring Boot, Spring Security 6, Spring Data JPA и PostgreSQL.

---

## 1. Параметры запуска и переменные окружения

Приложение поддерживает конфигурирование через переменные среды:
- `DB_URL` — адрес подключения к PostgreSQL (по умолчанию: `jdbc:postgresql://localhost:5432/auction_db`)
- `DB_USER` — пользователь БД (по умолчанию: `postgres`)
- `DB_PASSWORD` — пароль БД (по умолчанию: `postgres`)
- `ADMIN_PASSWORD` — пароль создаваемого сидером администратора `admin` (по умолчанию: `AdminPass123!`)

---

## 2. Предметная модель (Основные сущности)

- **User (`users`)** — участник аукциона с ролями (`ROLE_USER`, `ROLE_ADMIN`) и статусом аккаунта (`ACTIVE`, `BLOCKED`).
- **CollectibleItem (`collectible_items`)** — предмет коллекционирования (название, описание, текущий владелец `owner`, состояние).
- **AuctionLot (`auction_lots`)** — аукционный лот, привязанный к предмету. Содержит стартовую цену, шаг ставки, временные рамки и статус (`CREATED`, `ACTIVE`, `CLOSED`, `CANCELLED`).
- **Bid (`bids`)** — ставка участника в рамках конкретного лота с фиксацией времени и суммы.
- **AuctionDeal (`auction_deals`)** — сделка по итогам торгов. Связывает лот, победную ставку и статус передачи права собственности (`PENDING`, `TRANSFERRED`, `CANCELLED`).

---

## 3. Реализованные бизнес-операции

Все ключевые сценарии торгов изолированы в сервисе `AuctionBusinessService` и выполняются транзакционно (`@Transactional`):

1. **Активация лота (`POST /api/business/lots/{id}/activate`)**  
   Проверяет корректность дат и начальный статус (`CREATED`). Переводит лот в статус `ACTIVE` для открытия приёма ставок.
2. **Размещение ставки (`POST /api/business/lots/{id}/bids`)**  
   Проверяет активность лота, валидирует минимальный шаг `bidStep` и запрещает владельцу лота ставить на свой же предмет. Ставка автоматически связывается с текущим аутентифицированным пользователем.
3. **Закрытие торгов и формирование сделки (`POST /api/business/lots/{id}/close`)**  
   Переводит лот в статус `CLOSED`. При наличии ставок автоматически создаёт сделку `AuctionDeal` со статусом `PENDING`. Если ставок не было, лот закрывается без создания сделки (возвращается 204 No Content).
4. **Исполнение сделки и передача права собственности (`POST /api/business/deals/{id}/complete`)**  
   Переводит сделку в статус `TRANSFERRED` и передаёт право собственности на предмет победителю торгов (покупателю).
5. **Отмена лота (`POST /api/business/lots/{id}/cancel`)**  
   Досрочно переводит лот в статус `CANCELLED`. Запрещена, если сделка уже исполнена (`TRANSFERRED`); незавершённая сделка (`PENDING`) автоматически аннулируется.

## 4. Архитектура безопасности

1. **Аутентификация:**
    - HTTP Basic Auth в режиме Stateless.
    - Пароли хешируются с использованием `BCryptPasswordEncoder`.
    - Учёт состояния аккаунта: при статусе `BLOCKED` доступ запрещается с кодом `401 Unauthorized`.
    - Унифицированный JSON-ответ при ошибках аутентификации без раскрытия причин отказа.

2. **Ролевой и контекстный доступ:**
    - Роли: `ROLE_USER` и `ROLE_ADMIN`.
    - Тонкая проверка прав через `@PreAuthorize` и SpEL-бин `@authz` (`AuthzChecks`):
        - Создание лота разрешено только владельцу предмета (`@authz.isItemOwner`) или администратору.
        - Активация, закрытие и отмена лота разрешены только продавцу (`@authz.isLotSeller`) или администратору.
        - Изменение и удаление ставки разрешено только её автору (`@authz.isBidAuthor`) или администратору.
        - Просмотр сделки разрешён только её участникам (`@authz.isDealParticipant`) или администратору.
        - Просмотр всех пользователей и ручное изменение статуса лотов — только `ROLE_ADMIN`.
        - ID создателя ставок и предметов берётся напрямую из `SecurityContextHolder` (`CurrentUser`), что предотвращает подмену идентификатора (IDOR/BOLA).

3. **Защита персональных данных (DTO):**
    - Хеши паролей исключены из сериализации.
    - В публичных ответах ставок и карточек предметов используется `UserDto.Public(id, username)`, что исключает утечку email-адресов посторонним пользователям.

4. **Защита от CSRF:**
    - Настроена через `CookieCsrfTokenRepository.withHttpOnlyFalse()` и фильтр `CsrfCookieFilter`.
    - Для всех небезопасных HTTP-методов (`POST`, `PATCH`, `DELETE`) требуется заголовок `X-XSRF-TOKEN`. Публичный токен запрашивается через открытый эндпоинт `GET /api/auth/csrf`.

5. **Политика сложности паролей:**
    - Длина от 10 символов.
    - Обязательное наличие заглавной буквы, строчной буквы, цифры и специального символа.
    - Запрещено совпадение пароля с логином пользователя.

6. **Обработка ошибок:**
    - `401 Unauthorized`: неверные учётные данные или заблокированный аккаунт.
    - `403 Forbidden`: недостаточно прав или отсутствует/невалиден CSRF-токен.
    - `400 Bad Request`: нарушение валидации входных данных или политики сложности пароля.
    - `409 Conflict`: дубликаты логина/email и бизнес-конфликты без раскрытия внутренней структуры БД.
    - Системный адрес `/error` открыт, внутренние трассировки стека скрыты.

## 5. Матрица доступа (RBAC)

| Операция | Эндпоинт | Anonymous | USER | ADMIN | Примечание |
|---|---|:---:|:---:|:---:|---|
| Получение CSRF | `GET /api/auth/csrf` | 200 OK | 200 OK | 200 OK | Публичный доступ |
| Регистрация | `POST /api/auth/register` | 201 Created | 201 Created | 201 Created | Назначается роль USER |
| Профиль текущего пользователя | `GET /api/auth/me` | 401 | 200 OK | 200 OK | Возвращает данные текущей сессии |
| Список всех пользователей | `GET /api/users` | 401 | 403 Forbidden | 200 OK | Только для администратора |
| Блокировка / свитч роли | `PATCH /api/users/{id}` | 401 | 403 Forbidden | 200 OK | Менять role/status может только ADMIN |
| Создание предмета | `POST /api/collectible-items` | 401 | 201 Created | 201 Created | Владелец = текущий пользователь |
| Редактирование предмета | `PATCH /api/collectible-items/{id}` | 401 | Только владелец | 200 OK | Проверка `@authz.isItemOwner` |
| Создание лота | `POST /api/auction-lots` | 401 | Только владелец | 201 Created | Проверка принадлежности предмета |
| Ручная смена статуса лота | `PATCH /api/auction-lots/{id}` | 401 | 403 Forbidden | 200 OK | Только администратор |
| Активация/закрытие лота | `POST /api/business/lots/{id}/*` | 401 | Только продавец | 200 OK | Проверка `@authz.isLotSeller` |
| Размещение ставки | `POST /api/business/lots/{id}/bids` | 401 | 200 OK | 200 OK | Автор ставки = текущий пользователь |
| Завершение сделки | `POST /api/business/deals/{id}/complete` | 401 | Только продавец | 200 OK | Проверка `@authz.isDealSeller` |

> **Особенность логики передачи прав:** после успешного вызова `/complete` право собственности на предмет переходит победителю торгов (покупателю). Бывший владелец (продавец) теряет доступ к изменению и удалению данного предмета и при последующих попытках получает `403 Forbidden`.

## 6. Тестирование (Postman)

В директории `postman/auction.postman_collection.json` находится синхронизированная коллекция автотестов Postman (все 64 теста выполняются со статусом 100% Passed):
1. **0. Auth** — получение CSRF-токена, регистрация динамических пользователей через `{{$timestamp}}`, проверки 400 и 409, валидация 401 при неверном пароле.
2. **1. users** — администрирование пользователей и проверка прав.
3. **2. collectible-items, 3. auction-lots** — создание и редактирование сущностей под учётной записью продавца.
4. **4. Бизнес-сценарий (лаба 3)** — сквозной процесс: активация лота $\rightarrow$ ставка покупателя $\rightarrow$ закрытие торгов $\rightarrow$ проведение сделки $\rightarrow$ подтверждение смены владельца.
5. **5. bids, 6. auction-deals** — верификация созданных ставок и сделок по сохранённым динамическим ID.
6. **7. Проверки безопасности и RBAC** — комплекс негативных проверок: запросы без авторизации (401), запросы без CSRF (403), попытки эскалации привилегий, доступ обычного пользователя к админ-ресурсам (403), блокировка учётной записи с последующим запретом входа (401).
7. **8. каскадное удаление** — изолированный тест удаления связанных сущностей администратором.
