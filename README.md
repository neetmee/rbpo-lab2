# Лабораторная работа №5: JWT Access/Refresh и управление сессиями

RESTful веб-приложение для проведения торгов редкими и коллекционными предметами. Реализовано на стеке Spring Boot, Spring Security, Spring Data JPA, JJWT (`HS256`) и PostgreSQL.

---

## 1. Параметры запуска и переменные окружения

Приложение поддерживает конфигурирование через переменные среды:
- `DB_URL` — адрес подключения к PostgreSQL (`jdbc:postgresql://localhost:5432/auction_db`)
- `DB_USER` — пользователь БД (`postgres`)
- `DB_PASSWORD` — пароль БД
- `ADMIN_PASSWORD` — пароль создаваемого сидером администратора `admin` (по умолчанию: `AdminPass123!`)
- `JWT_SECRET` — секретный ключ в формате Base64 (не менее 32 случайных байт для алгоритма `HS256`; в репозиторий не сохраняется)

В `application.yaml` заданы сроки жизни токенов (в миллисекундах):
- `jwt.accessExpiration` — по умолчанию `900000` (15 минут)
- `jwt.refreshExpiration` — по умолчанию `604800000` (7 суток)

---

## 2. Предметная модель (Основные сущности)

- **User (`users`)** — участник аукциона с ролями (`ROLE_USER`, `ROLE_ADMIN`) и статусом аккаунта (`ACTIVE`, `BLOCKED`).
- **UserSession (`user_sessions`)** — серверная запись выданной пары токенов (`id` UUID, `username`, `device_id`, `access_token`, `refresh_token` с ограничением `UNIQUE`, `access_token_expiry`, `refresh_token_expiry`, `status`: `ACTIVE`, `USED`, `REVOKED`).
- **CollectibleItem (`collectible_items`)** — предмет коллекционирования (название, описание, текущий владелец `owner`, состояние).
- **AuctionLot (`auction_lots`)** — аукционный лот, привязанный к предмету. Содержит стартовую цену, шаг ставки, временные рамки и статус (`CREATED`, `ACTIVE`, `CLOSED`, `CANCELLED`).
- **Bid (`bids`)** — ставка участника в рамках конкретного лота с фиксацией времени и суммы.
- **AuctionDeal (`auction_deals`)** — сделка по итогам торгов. Связывает лот, победную ставку и статус передачи права собственности (`PENDING`, `TRANSFERRED`, `CANCELLED`).

---

## 3. Реализованные бизнес-операции

Все ключевые сценарии торгов изолированы в сервисе `AuctionBusinessService` и выполняются транзакционно (`@Transactional`):

1. **Активация лота (`POST /api/business/lots/{id}/activate`)**  
   Проверяет корректность дат и начальный статус (`CREATED`). Переводит лот в статус `ACTIVE` для открытия приёма ставок.
2. **Размещение ставки (`POST /api/business/lots/{id}/bids`)**  
   Проверяет активность лота, валидирует минимальный шаг `bidStep` и запрещает владельцу лота ставить на свой же предмет. Ставка автоматически связывается с текущим аутентифицированным пользователем.
3. **Закрытие торгов и формирование сделки (`POST /api/business/lots/{id}/close`)**  
   Переводит лот в статус `CLOSED`. При наличии ставок автоматически создаёт сделку `AuctionDeal` со статусом `PENDING`. Если ставок не было, лот закрывается без создания сделки (возвращается 204 No Content).
4. **Исполнение сделки и передача права собственности (`POST /api/business/deals/{id}/complete`)**  
   Переводит сделку в статус `TRANSFERRED` и передаёт право собственности на предмет победителю торгов (покупателю).
5. **Отмена лота (`POST /api/business/lots/{id}/cancel`)**  
   Досрочно переводит лот в статус `CANCELLED`. Запрещена, если сделка уже исполнена (`TRANSFERRED`); незавершённая сделка (`PENDING`) автоматически аннулируется.

## 4. Архитектура безопасности

1. **Аутентификация по JWT (`HS256`) и режим `STATELESS`:**
   - HTTP Basic Auth и CSRF-защита отключены: `accessToken` передаётся в заголовке `Authorization: Bearer <accessToken>`, а `refreshToken` — в JSON-теле запроса `POST /api/auth/refresh`.
   - Оба токена формируются в виде подписанных JWT (`alg: HS256`) с claims `sub` (`username`), `type` (`"access"` или `"refresh"`), `jti` (`UUID.randomUUID()`), `iat` и `exp` (с точностью до секунд).
   - `JwtTokenFilter` пропускает только токены с `type = "access"`, проверяет подпись, срок действия и обязательные claims, а также актуальное состояние пользователя (`isEnabled()`, `isAccountNonLocked()`). При блокировке аккаунта доступ по ранее выданному токену отклоняется с кодом `401 Unauthorized`.
   - Пароли хешируются с использованием `BCryptPasswordEncoder`.

2. **Ротация refresh-токенов и статусы сессий:**
   - При входе (`POST /api/auth/login`) и регистрации (`POST /api/auth/register`) создаётся пара `accessToken` / `refreshToken` и сохраняется сессия со статусом `ACTIVE`.
   - При обновлении (`POST /api/auth/refresh`) запись сессии выбирается с блокировкой (`PESSIMISTIC_WRITE`), прежняя сессия переводится в статус `USED`, а для новой пары создаётся отдельная строка со статусом `ACTIVE` (с теми же `username` и `deviceId`).
   - Повторное предъявление уже использованного (`USED`) `refreshToken` переводит эту сессию в статус `REVOKED` (сохраняется даже при возврате ошибки) и отклоняется с кодом `401 Unauthorized`; уже отозванная (`REVOKED`) сессия также возвращает `401`.
   - > **Примечание о хранении `refreshToken` в БД:** в соответствии с условиями задания `refreshToken` хранится в таблице `user_sessions` в открытом виде (с ограничением `UNIQUE`). В промышленной эксплуатации вместо хранения сырого токена в БД предпочтительно сохранять его криптографический хэш.

3. **Ролевой и контекстный доступ:**
   - Роли: `ROLE_USER` и `ROLE_ADMIN`.
   - Тонкая проверка прав через `@PreAuthorize` и SpEL-бин `@authz` (`AuthzChecks`):
      - Создание лота разрешено только владельцу предмета (`@authz.isItemOwner`) или администратору.
      - Активация, закрытие и отмена лота разрешены только продавцу (`@authz.isLotSeller`) или администратору.
      - Изменение и удаление ставки разрешено только её автору (`@authz.isBidAuthor`) или администратору.
      - Просмотр сделки разрешён только её участникам (`@authz.isDealParticipant`) или администратору.
      - Просмотр всех пользователей и ручное изменение статуса лотов — только `ROLE_ADMIN`.
      - Идентификатор текущего пользователя берётся из `SecurityContextHolder` (`CurrentUser`), что предотвращает подмену идентификатора (IDOR/BOLA).

4. **Защита персональных данных (DTO):**
   - Хеши паролей исключены из сериализации.
   - В публичных ответах ставок и карточек предметов используется `UserDto.Public(id, username)`, что исключает утечку email-адресов посторонним пользователям.

5. **Политика сложности паролей:**
   - Длина от 10 символов.
   - Обязательное наличие заглавной буквы, строчной буквы, цифры и специального символа.
   - Запрещено совпадение пароля с логином пользователя.

6. **Обработка ошибок:**
   - `400 Bad Request`: отсутствующие/пустые обязательные поля, нарушение валидации входных данных или политики сложности пароля.
   - `401 Unauthorized`: неверные учётные данные, заблокированный аккаунт, невалидный/просроченный JWT, неподходящий `type` токена, неизвестная/использованная/отозванная refresh-сессия.
   - `403 Forbidden`: недостаточно прав (`JsonAccessDeniedHandler` / `AccessDeniedException`).
   - `409 Conflict`: дубликаты логина/email и бизнес-конфликты без раскрытия внутренней структуры БД.
   - Ошибочные ответы не содержат токенов; системный адрес `/error` открыт, внутренние трассировки стека скрыты.

## 5. Матрица доступа (RBAC)

| Операция | Эндпоинт | Anonymous | USER | ADMIN | Примечание |
|---|---|:---:|:---:|:---:|---|
| Вход | `POST /api/auth/login` | 200 OK | 200 OK | 200 OK | Выдаёт пару `{accessToken, refreshToken}` |
| Регистрация | `POST /api/auth/register` | 201 Created | 201 Created | 201 Created | Создаёт пользователя (`USER`) и выдаёт пару токенов |
| Обновление токенов | `POST /api/auth/refresh` | 200 OK | 200 OK | 200 OK | Ротация по `refreshToken` из тела запроса (`401` при невалидном/использованном/отозванном) |
| Профиль текущего пользователя | `GET /api/auth/me` | 401 | 200 OK | 200 OK | Требует `Bearer <accessToken>` |
| Список всех пользователей | `GET /api/users` | 401 | 403 Forbidden | 200 OK | Только для администратора |
| Блокировка / свитч роли | `PATCH /api/users/{id}` | 401 | 403 Forbidden | 200 OK | Менять role/status может только ADMIN |
| Создание предмета | `POST /api/collectible-items` | 401 | 201 Created | 201 Created | Владелец = текущий пользователь |
| Редактирование предмета | `PATCH /api/collectible-items/{id}` | 401 | Только владелец | 200 OK | Проверка `@authz.isItemOwner` |
| Создание лота | `POST /api/auction-lots` | 401 | Только владелец | 201 Created | Проверка принадлежности предмета |
| Ручная смена статуса лота | `PATCH /api/auction-lots/{id}` | 401 | 403 Forbidden | 200 OK | Только администратор |
| Активация/закрытие лота | `POST /api/business/lots/{id}/*` | 401 | Только продавец | 200 OK | Проверка `@authz.isLotSeller` |
| Размещение ставки | `POST /api/business/lots/{id}/bids` | 401 | 200 OK | 200 OK | Автор ставки = текущий пользователь |
| Завершение сделки | `POST /api/business/deals/{id}/complete` | 401 | Только продавец | 200 OK | Проверка `@authz.isDealSeller` |

> **Особенность логики передачи прав:** после успешного вызова `/complete` право собственности на предмет переходит победителю торгов (покупателю). Бывший владелец (продавец) теряет доступ к изменению и удалению данного предмета и при последующих попытках получает `403 Forbidden`.

## 6. Тестирование (Postman)

В директории `postman/auction_lab5.postman_collection.json` находится обновлённая коллекция запросов и автотестов Postman:
1. **0. Auth** — вход администратора, регистрация продавца и покупателя с получением пары токенов (`201`) и определением `id` через `GET /api/auth/me`.
2. **1. Сценарий ротации и сессий (5 шагов задания)** — `login` → защищённый запрос с `accessToken` (`200`) → `refresh` (новая пара, строки отличаются) → повторный старый `refresh` (`401` без новой пары) → проверка статусов `REVOKED` / `ACTIVE` в `user_sessions`.
3. **2. Негативные проверки JWT и авторизации** — запросы без токена (`401`), пустые поля (`400`), неверный пароль (`401`), дубликат регистрации (`409`), `accessToken` в теле `/refresh` (`401`), `refreshToken` в `Bearer` (`401`), мусорный токен (`401`).
4. **3. Блокировка пользователя (Тест 7.2)** — вход покупателя → блокировка администратором → обращение по живому `accessToken` (`401`) и повторный вход (`401`) → разблокировка.
5. **4. Аукцион и RBAC** — проверки ролей и прав по `Bearer`-токенам.
